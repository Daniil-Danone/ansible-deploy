# Работа с ветками

Единый флоу для всех проектов. Репозитории, в которых ведётся работа,
перечислены в `flow/PROJECT.md`.

```
main      продовая ветка
develop   основная ветка разработки
feature/* fix/*  ветки от develop
```

## Перед работой

1. **Актуализировать** `develop` во **всех** репозиториях, где будет вестись
   работа: `git -C <repo> fetch --prune && git -C <repo> checkout develop && git -C <repo> pull`.
2. **Подчистить ветки**, уже смерженные в `develop` и не находящиеся в работе.
   Перед удалением проверить, не ведёт ли по ветке работу другой агент или
   сессия: свежие коммиты, незапушенные изменения, открытый PR.
   **Сомневаешься — не удаляй, спроси в чате.**
3. Создать ветку от свежего `develop`.

## По ходу

- Коммиты по Conventional Commits: `feat:` `fix:` `refactor:` `chore:` `docs:`
  `test:` `ci:`. Заголовок + тело: что сделано и **зачем**.
- Первый пуш — `git push --set-upstream origin <branch>`.
- Одна ветка — один связный кусок. Несколько независимых фич — несколько веток,
  можно делать подряд.
- **Если фича Y зависит от фичи X, которая ещё не в `develop`** — остановиться и
  сказать в чате: нужен PR из ветки X в `develop` и локальная актуализация.
  Не ветвиться от ветки без явного разрешения.
- Правки по фиче, чья ветка локально уже удалена, — **новая ветка с новым
  именем**, чтобы не ловить конфликт с уже смерженной.

## После работы

Подчистить за собой ветки, которые уже запушены и вмержены.

Отчёт должен содержать три списка (шаблон — в `/ship`):

1. **PR в порядке мержа** — с указанием, почему именно такой порядок, если он
   важен (фронт после бэка, миграция до кода, и так далее).
2. **Что настроить руками** — переменные окружения, значения в админке,
   секреты, доступы, ручные миграции. Блоком 🛠️ в чате, пунктами в
   `flow/MANUAL.md` и артефактом-инструкцией — по
   [reporting.md](reporting.md).
3. **Что сделано и как проверено** — по пункту на фичу, с командой или
   наблюдением, которое это подтверждает.

## Коммиты и пуш

Коммитить и пушить в рабочую ветку — самостоятельно, по ходу работы.
PR в `develop`/`main` агент **открывает и мержит сам** через `gh` — но только
по зелёному CI (условие ниже). Это разрешение действует внутри фреймворка и
отменяет общий запрет, если он записан в `CLAUDE.md` проекта: здесь за мержем
стоят гейты шага, отметка в `log/` и `flow-lint`, а не одна внимательность.

Чего агент не делает никогда: не мержит с красным или незавершённым CI, не
обходит проверки, не трогает чужой PR и ветку, по которой идёт работа.
Проверка не сходится — стоп и в чат, а не «похоже, флейк».

Если владелец разрешил агенту мержить и в репозитории есть CI — мерж только
при **всех зелёных проверках** (`gh pr checks <PR> --watch`). Исключения из
этого правила — только те, что записаны решением в `flow/DECISIONS.md`;
здесь их не дублируем. На бесплатном
тарифе GitHub обязательные проверки для приватных репозиториев не включить, и
тогда эта дисциплина — единственное, что не пускает красный код в `develop`.

Строку `Co-Authored-By` в коммиты не добавлять.

## Несколько репозиториев

Если работа задевает несколько репозиториев (бэкенд и клиент), то в каждом —
своя ветка, свои коммиты и свой PR. В отчёте всегда указывать, **в какой
репозиторий** идёт коммит. Порядок мержа между репозиториями почти всегда
важен: клиент, ушедший в прод раньше сервера, ломает продакшн.
