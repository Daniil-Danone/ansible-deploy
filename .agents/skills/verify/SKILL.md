# /verify

Ревью стоит дорого. Половина того, за чем его зовут, — мусор в дифе,
проглоченные ошибки, забытый `print`, переносы строк — ловится текстом и
регулярками бесплатно. Поэтому: **сначала дешёвое, дорогое — только если
дешёвое нашло повод.**

Запускается после реализации: в конце шага `/go`, в конце захода `/go N-M`,
и вручную, когда надо ответить на «а точно готово».

## 1. Механика — ноль токенов

```
python .codex/tools/verify.py --fix
```

`--fix` сам откатывает файлы, в которых изменились только пробелы и переносы
строк: это единственная находка, которую можно починить механически и без
риска — содержимое там тождественно, меняется только форматирование.

Смотрит диф рабочего дерева против `HEAD` (для захода или ветки целиком —
`--base develop`). Ищет: файлы, где изменились только пробелы и переносы;
секреты и файлы окружения; отладочный мусор и `TODO`; проглоченные ошибки;
тронутые зависимости и миграции; крупные дифы; и какие **зоны риска** из
`flow/PROJECT.md` задеты.

Код возврата: `0` — чисто, `1` — есть находки или задета зона риска.

Блокирующее (`.env`, секрет, диф из одних переносов строк) чинится **здесь
же**, до всего остального. Дальше не идём.

## 2. Проверки проекта — командами из `PROJECT.md`

Форматтер проекта — первым, **один раз здесь**, а не после каждой правки:
так он не спорит с работающим агентом и не плодит расхождений посреди шага.
Дальше линтер, типы и **точечные** тесты по затронутым модулям — в тихой
форме, как записано в `## Команды`. Полный прогон тестов — не здесь, он на
`/ship`.

На Windows стоит один раз завести `.gitattributes` с `* text=auto eol=lf`:
без него переносы строк уезжают в диф сами, и `--fix` будет откатывать файлы
на каждом шаге.

Критерий шага из `plan.md` доказывается тем, что записано в `Готово:`, и
строки `tests.md`, закрытые этим шагом, заполняются.

Красное — чиним и перепрогоняем. Не «наверное, флака»: упавший тест либо
чинится, либо признаётся сломанным с объяснением.

## 3. Ревьюер — только по поводу

Зовём `reviewer`, если выполнено хоть что-то:

- `verify.py` вернул `1` из-за находок, которые не снялись правкой;
- диф задел **зону риска** — тогда гейты уровня 1 по
  [gates.md](../../../.codex/guidelines/gates.md) целиком, а не только ревьюер, и
  результат записывается в `log/` строкой `Гейты: зона «…» — …`; без неё
  `flow-lint` не даст закоммитить;
- шаг трогал интерфейс — лестница проверки интерфейса оттуда же, ступень 1
  обязательна;
- сам не уверен в решении и можешь назвать, в чём именно.

Во всех остальных случаях ревьюер не нужен, и это нормальный, самый частый
исход. Ревью «на всякий случай» — это плата без выгоды.

## 4. Цикл исправления — не больше двух кругов

Ревьюер нашёл — чиним и **перепрогоняем `/verify` с первого шага**: правка
могла привнести новое. Ревьюер повторно смотрит только то, что менялось.

Больше двух кругов не крутим. Не сошлось за два — останавливаемся и
показываем владельцу: что нашли, что чинили, почему не сходится. Третий круг
почти всегда значит, что проблема в задании, а не в коде.

## Отчёт

Короткий, в чат:

```
verify: чисто · линтер ok · типы ok · тесты 12 passed
критерий: <как доказан>
```

или

```
verify: 2 находки
  БЛОКИРУЕТ  app/util/other.py — только переносы строк → откатил
  внимание   app/billing/charge.py — зона «деньги» → reviewer
reviewer: 1 находка, исправлена (<что>), перепрогнал — чисто
критерий: <как доказан>
```

## Правила

- Механика — всегда первой. Звать ревьюера, не прогнав `verify.py`, нельзя:
  он потратит дорогой проход на то, что видно бесплатно.
- Тесты — точечные по затронутому, не весь набор. Полный — на `/ship`.
- Вывод команд — в тихой форме: он оплачивается до конца сессии.
- «Проверил визуально» проверкой не считается. Считается вывод команды.
- Находка, которую решено не чинить, называется вслух с причиной — молча
  проигнорировать нельзя.
